# Project review — 1 October 2026

## Result and scope

Reviewed the application entry points, provider/parser boundary, action dispatch,
command execution, file operations, persistence, approvals, device adapters, voice,
normal web UI/API, 3D viewer, Satellite API/client/storage/pairing, installer,
dependencies, tests and security documentation. This is a code review with targeted
regression and integration testing, not a certification that every external service
or hardware combination works.

Baseline: 102 tests passed before edits. Final suite: 112 passing tests on Python
3.14. Core functionality remains on `feature/satellite-beta`; main is unchanged.

## Issues fixed

| Finding | Resolution |
| --- | --- |
| TV mode required remembering standalone CLI flags | Added setup-first TV controls to both normal menus and `/tv` during terminal chat. |
| No shared TV lifecycle across normal interfaces | One PC controller launches a separate restricted process, reports readiness/failure, stops only its own child, and preserves it across interface changes. Normal application exit cleans it up. |
| Immediate stop/start could fail after a connection | POSIX Satellite sockets now use address reuse before binding; restart and persistent credentials tested. |
| Prose containing a JSON action example could execute | Only a complete response envelope, optionally fenced, can request an action. Prose extraction is display-only. Oversized/deeply nested response parsing is bounded. |
| Terminal command capture could accumulate unlimited output and handle timeout differently from web | All foreground shell/Kali commands use the existing bounded stream collector. POSIX timeout/interruption terminates the process group. Background mode requires a real boolean. |
| Special-file reads could block or never end | Nonblocking, no-final-symlink open where supported; reject non-regular files; read at most 1 MB plus a size-check byte. |
| File-edit backup initially used default permissions | Create the exclusive backup using source permissions before writing contents. |
| 3D viewer lacked host/origin protection | Validate local authority and same origin for HTTP and WebSocket; block non-JSON writes. |
| Local chat did not bound request bodies before validation | Shared local guard rejects duplicate security headers, compressed bodies and oversized/chunked requests, with a body-read deadline. Authentication still precedes parsing. |
| Skill report always claimed terminal confirmation | Report correctly states that execution follows the current session approval setting. |
| Installed pip had known vulnerability advisories | Updated only JARVIS virtualenv pip from 26.1.1 to 26.2.1; installer now updates pip to at least 26.2 before installing project packages. |

## TV user flow

- Web: interface menu → **TV mode · setup & controls**.
- Terminal: `jarvis --menu` → **6) TV mode**; or type `/tv` in text chat.
- Read the setup instructions before starting. PC preview binds loopback and cannot
  connect a TV. HTTPS mode needs a private IP and matching, TV-trusted certificate/key.
- Start displays readiness, address and a one-use, five-minute pairing code. Close
  the panel to continue normal chat while TV mode runs. Stop disconnects clients
  while preserving their saved data. Stop/start renews the code.
- The menu is an explicit session opt-in; it does not write `.env`. The standalone
  CLI retains its explicit enable flag. Independently launched Satellite processes
  must be stopped in their own terminal; the menu does not adopt arbitrary processes.
- The authenticated PC API controls the child process. No control endpoints or PC
  tools are added to the LAN API. Pairing codes stay in memory and out of AI/chat data.

## Validation performed

- 112 automated tests: original regression suite plus parser execution boundaries,
  special-file rejection, bounded command output/timeout, viewer HTTP/WebSocket
  origin checks, TV terminal setup ordering, PC API authentication/validation,
  real process preview/pairing/stop/restart/resume, occupied-port failure and real
  certificate-verified HTTPS pairing. Tests use disposable storage and local ports.
- Real Ollama cloud conversation returned nonempty text with no action requested.
  Other provider routes retain mock coverage; no paid-provider requests were made.
- Chromium: normal web loads without JavaScript errors; menu and setup dialog render;
  preview starts, shows the running address, stops, and re-enables setup controls;
  HTTPS fields appear and wildcard binding produces a visible validation error.
- `pip check`: no broken dependencies. `pip-audit` after the pip update: no known
  vulnerabilities in the installed environment at scan time. The earlier four
  advisory records represented two duplicated pip advisory IDs.
- Bandit static scan reviewed: remaining shell/subprocess warnings are intentional
  command-launch features, and SQL string warnings interpolate only generated `?`
  placeholders with all user values bound separately. These were not silently
  suppressed. Satellite's exception fallback intentionally avoids logging secrets.
- Publication secret checker and whitespace checks run before commit. No `.env`,
  device credentials, databases, private certificates or test audio are published.

## Component review and practical limits

| Area | Assessment / remaining boundary |
| --- | --- |
| `main.py`, `terminal_ui.py`, `session.py` | Menu routing, scoped approvals, local commands and recalled inputs tested. Auto-approval resets on restart. |
| `brain.py`, `config.py`, `privacy.py`, `presentation.py` | Provider context is scoped; known credentials redacted; response envelope parsed defensively. Redaction is best-effort, not a guarantee for arbitrary secrets. Gemini default checked against [Google's model documentation](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash). |
| `actions.py`, `execution.py`, `tool_inventory.py` | Explicit approvals and bounded foreground capture. Shell execution intentionally retains OS-user privileges; blacklist is not a sandbox. Detached jobs remain separate. Optional inventory presence is not a functional tool test. |
| `file_tools.py` | Exclusive creation, bounded reads and backup edits. File checks are not a complete filesystem sandbox or protection against a malicious same-account process racing directory changes. |
| `memory.py`, `chat_store.py` | Parameterized SQL, private database, bounded AI context, saved-chat pin/delete/resume tested. Visible saved chats grow until deleted; database is not encrypted. General PC memory is shared across normal interfaces. |
| `web_chat.py`, `local_security.py`, `web/*` | Token-authenticated loopback API, host/origin/input guards, text-only model rendering, saved chats, approvals and execution monitor tested. No multi-user server isolation; keep PC launch tokens private. |
| `satellite/*`, `web/satellite/*`, `tv_mode.py` | Separate conversation-only service with strict auth, pairing, validation and tool denial. An OS force-kill/power loss cannot run parent cleanup. HTTPS trust and actual LAN connectivity still depend on device/network setup. |
| `devices.py` | Android shell arguments quoted; device selection/phone actions validated. iOS supports USB listing/info only. Real devices and Bluetooth pairing are not available for this review. |
| `voice.py` | Existing microphone reuse, recognizer timeout, TTS fallback and adapter tests pass. Actual microphones/speakers and service availability are not proven by mocks. Browser speech is optional and may use the browser vendor's service. |
| `viewer.py`, `render_server.py`, `static/*` | Scene validation and viewer broadcast tested; same-origin browser access enforced. Three.js still loads from its pinned CDN URL; offline/CDN-unavailable rendering is a remaining limitation. |
| `web_research.py`, `diagnostics.py` | Search snippets treated as data; unsafe URL schemes removed; unavailable search reports failure honestly. Live search and optional installed tools were not exhaustively exercised. |
| `scripts/*`, requirements and CI | Installer uses current interpreter, isolated venv and explicit launcher. Existing dependency bounds remain; audit reflects installed versions, not all versions permitted by those bounds. |

## How the owner can help finish hardware validation

1. Try **PC preview** first, then supply the TV model/browser and the PC's actual
   private IP when testing HTTPS. Do not send private key contents.
2. Check typing, remote focus navigation, reconnect after stopping/starting and
   optional browser microphone/read-aloud on the TV. Report exact visible errors.
3. Connect/authorize Android or iPhone by USB, or enable a Bluetooth adapter, to
   validate those optional integrations. Voice testing requires an available input
   device and speakers.

A future remote-PC-control feature needs a separate least-privilege action gateway,
explicit per-device grants and fresh PC approval; it must not inherit global
terminal privileges or be enabled by changing one capability flag.
